# Research screen (method E)

Research screen: 2 tabs, 96 items, 96 details (method E)

This is the largest example, assembled only from high-level parts. It has two tabs (needs research, researched), a 6x8 grid of cells and pager buttons on each tab, and a detail prebuilt for every cell. Together they make 2022 buttons (96 cells, 2 tabs, 4 pager buttons, and 96 details x 20). The screen code has no button indices and no `slots`, and the server opens it with a single `openScreen` call.

## How the screen is put together

| Part | Component | What it does |
| --- | --- | --- |
| Tabs | `<Tabs mode="follow">` + `<Tab>` | The tab row on top. Each tab has its own grid and pager buttons |
| Cell grid | `<SelectGrid name rows cols detail>` | One cell is one record. Choosing a cell shows its detail in the right pane |
| Pages | `<Pager name>` | Previous and next arrows on the bottom row of the left pane |
| Hint | `<Placeholder text>` | The hint text in the right pane before you choose a cell |
| Detail | `<DetailPanel>` holding `IconTitle`, `TextBlock`, `IconRow`, `Spacer`, `ActionButton` | The detail in the right pane. `ItemDetail` below stacks them |

The screen uses `layout="split"`: tabs and the grid go in the left pane, and the detail goes in the right pane.

### ItemDetail: a custom component

`ItemDetail` is a function with no arguments that returns one `<DetailPanel>`. You build your own detail screen the same way.

1. Wrap everything in `<DetailPanel footer={...}>`. The children are a scrolling body stacked top to bottom, and `footer` stays fixed below it.
2. Stack small parts in the body. Each part points to one or more fields of the record by name. `<IconTitle name="name" subtitle="status" />` uses the record's `name`, `status` and `icon`, and `<TextBlock name="desc" />` uses `desc`.
3. Put gaps between parts with `<Spacer h={...} />`.
4. The fixed button at the bottom is `<ActionButton name="action" />`. Pressing it returns `{ name: <grid>, index: <cell>, field: "action" }`.
5. Pass the detail to `<SelectGrid detail={<ItemDetail />}>`. The grid renders this element once per cell.

Part names must not repeat inside one detail (a repeated field name is a build error). Note that the names are the record keys: `IconRow name="mats"` spreads the record's `mats` array over `count` cells (8 here).

## Server data

The data for `<SelectGrid name="needed">` is an array of records. One cell is one record, and the record keys match the names the detail parts use.

```js
// one record (one cell)
{
  icon: "textures/items/book_normal",          // the cell icon and the IconTitle icon
  name: "§cItem 1",                            // IconTitle name
  status: "§cNeeds research",                  // IconTitle subtitle
  desc: "Description of Item 1. ...",          // TextBlock desc
  mats: [["textures/items/coal", 3]],          // IconRow mats: [icon, count]
  rewards: ["textures/items/apple"],           // IconRow rewards: icon only (badge "+1" in the count spot)
  action: "Start research",                    // ActionButton action
}
```

Tab text and icons are the `tabs` array. Pager buttons show no text, so they take no data.

## Opening it from the server

The server builds the records and passes them to `openScreen`; to turn a page, it changes the data and opens the same screen again.

<Source data={serverSource} />

The response is `{ name, index, field? }`. Pressing a cell gives `{ name: "needed", index: 5 }`, and a button inside a detail adds `field` (for `ActionButton`, the part's `name`, `"action"`). A pager button gives `{ name: "neededPages", index: 0 }` (previous) or `index: 1` (next).

```js
import { decode } from "./generated/screens.js";

decode("research", 102 + 20 * 3 + 19); // { name: "needed", index: 3, field: "action" }
decode("research", 99);                // { name: "neededPages", index: 1 }
```

`LAYOUTS["research"]` in the generated module shows how the indices were divided (only the beginning is shown because it is long). Cells, tabs and pager buttons come first, then the detail blocks (20 per cell).

## Prebuilding a detail for every cell (method E)

The point of the research screen is to switch between 96 details **without a server round trip**. Sending a response to the server each time you pick a cell would close the form. So a detail is prebuilt for every cell, and only the chosen cell's is visible.

- The cells are radio toggles. The 96 cells of both grids share one `toggle_name`, so only one is on at a time (INP-12, INP-35).
- Inside the `checked` face of the cell that is on sits that cell's detail definition (INP-36). Turning a cell on draws its detail, and turning another on switches this face off and the detail goes away.
- The detail's position is shifted back by the cell's position so it lands on the right pane.
- A fixed `collection_index` only works if the cell is a direct child of a horizontal `stack_panel` with a `collection_name` (COL-38, COL-50).
- All text and icons in the detail are button data. Cells that cannot be pressed are still sent with `button()` (COL-19). The body reuses `common.scrolling_panel` (LAY-02, LAY-04).
- Indices are handed out by kind: cell grids, then buttons (tabs and pagers), then detail blocks. So `buildScreens` lowers the screen twice (the first pass only fixes the numbering order and is discarded).

## Output equivalence test

This screen began as a reproduction of the FFR original, written line by line with the low-level API. When it moved to the high-level API, the output was checked not to change, in three steps.

1. **The FFR original**: the original UI definitions (`faces.json`) and button layout (`102 + 20k + 19`) the server uses.
2. **The low-level reproduction**: a screen that carries those definitions over with `createSlots` and `createPack` (`tests/helpers/legacy-research.ts`).
3. **The high-level assembly**: `research.tsx` above.

The test (`tests/regression/research-high.test.tsx`) compares the **expanded trees** of the two. An expanded tree starts from the router root, resolves every inheritance (`@`), `$` variable and reference, and drops control names and definition names. If only the names differ, the trees count as equal. The difference is 0 (the allow list is empty), and a control case checks that the comparer catches a change to even one rendering property. The server side is compared too: the form that `openScreen` sends (title and 2022 buttons: text, icon and order) matches the original, and so does the handling of the pager and action-button responses.
